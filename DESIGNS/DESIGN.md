# 다녀오리 계절별 디자인 가이드

> 상태: 디자인 기준 문서 · 기본 테마: **봄** · 2026-07 색상 개정안과 웹 CSS 토큰 적용 완료 · 관리자 수동 테마 선택은 후속 작업에서 진행한다.

## 1. 문서 목적

다녀오리는 지역 축제를 **발견하고, 대표 프로그램을 10~30초 미니게임으로 미리 체험하고, 실제 주말 방문과 후기 공유로 이어지게 하는 O2O 서비스**다. 이 문서는 축제 목록, 축제 달력, 미니게임, 사전예약 화면이 계절감을 자연스럽게 전달하면서도 하나의 다녀오리 브랜드로 보이게 하는 기준이다.

계절 테마는 정보를 가리는 장식이 아니다. 날짜·장소·가격·혜택처럼 방문 결정에 필요한 정보를 우선 읽히게 하고, 그 주변의 표면·배지·이미지·보조 색으로 해당 축제의 분위기를 보완한다.

참고 방향은 [대한민국 구석구석](https://korean.visitkorea.or.kr/main/main.do)의 여행 서비스 탐색 구조다. 축제 달력, 진행 중 행사, 여행 코스처럼 여러 진입점을 명확히 구분하는 정보 위계와 넓은 여행 이미지의 활용만 참고한다. 화면 구성, 색, 컴포넌트를 그대로 복제하지 않는다.

## 2. 전체 디자인 원칙

1. **봄을 기본값으로 둔다.** 날짜가 없거나 복수 축제를 한 화면에서 동등하게 보여줄 때는 따뜻한 봄 기반의 공통 표면을 유지한다.
2. **밝은 계절색은 배경과 보조 강조에 쓴다.** 본문·날짜·가격·상태는 각 계절의 `--theme-text`처럼 충분히 진한 색을 사용해 대비를 확보한다.
3. **계절은 축제 경험을 설명해야 한다.** 꽃, 물, 수확, 눈처럼 실제 프로그램·장소·시기에 연결되는 소재만 사용한다.
4. **게임성과 여행 정보의 역할을 분리한다.** 픽셀 표현은 게임 진입·플레이·보상에 한정하고, 목록·달력은 차분한 여행 정보 UI를 우선한다.
5. **한 화면에 하나의 핵심 행동만 둔다.** 테마색은 CTA를 여러 개 경쟁시키는 용도가 아니다.
6. **색만으로 상태를 전달하지 않는다.** 개최 중, 마감 임박, 선택됨, 보상 획득은 텍스트·아이콘·형태를 함께 제공한다.
7. **계절 테마는 별칭 토큰으로 적용한다.** 기존 `--olive`, `--cream`, `--ink` 같은 기반 토큰을 화면마다 덮어쓰거나 삭제하지 않고, `--theme-*` 별칭만 바꾼다. 봄의 올리브를 여름·가을·겨울에 강제로 유지하지 않는다.

### 적용 범위와 우선순위

| 상황 | 권장 적용 |
| --- | --- |
| 홈·소개처럼 한 계절의 에디토리얼 메시지가 중심인 화면 | 페이지 배경, 히어로 보조색, CTA에 해당 계절 테마 적용 |
| 여러 달·여러 지역 축제가 함께 있는 목록 | 페이지는 기본 봄/중립 표면, 각 카드와 배지에 축제별 테마 적용 |
| 축제 상세·축제별 미니게임 | 해당 축제의 계절 테마를 헤더, 보상 패널, 소량의 장식에 적용 |
| 축제 달력 | 현재 보는 월의 테마를 약하게 적용하고, 날짜별 행사는 개별 배지로 구분 |
| 날짜 정보가 없거나 검증되지 않은 축제 | 기본 봄 테마와 중립 정보 스타일 사용 |

## 3. 공통 기반 토큰

봄 팔레트를 서비스의 기본값으로 사용하되, 계절이 명확한 화면에서는 배경·표면·주요 행동·보조 포인트·본문을 `--theme-*` 의미 토큰으로 교체한다. 다녀오리의 일관성은 모든 계절에 올리브색을 반복하는 방식이 아니라 동일한 타이포그래피, 여백, 정보 위계, 마스코트와 상호작용 규칙으로 유지한다.

```text
계절 공통 의미 토큰
--theme-page-bg · --theme-surface · --theme-primary · --theme-accent · --theme-text

선택 의미 토큰
--theme-secondary · --theme-sub-accent · --theme-soft · --theme-border
```

- `--theme-primary`: 주 CTA, 활성 탭, 핵심 정보 배지에 사용한다.
- `--theme-secondary`: 여름의 숲·계곡처럼 계절 안에서 분명한 두 번째 의미가 있을 때만 사용한다.
- `--theme-accent`, `--theme-sub-accent`: 배지 배경, 작은 장식, 보조 정보에 제한한다.
- `--theme-text`: 제목과 본문의 기본색이다. 밝은 계절색을 본문색으로 사용하지 않는다.
- 오류·경고·성공 같은 의미 기반 상태색은 계절 팔레트로 대체하지 않는다.

- 제목: `Pretendard`/`Noto Sans KR`, 굵기 700–800, 줄높이 1.15–1.25.
- 본문: 굵기 400–500, 줄높이 1.55–1.7. 파스텔 색 본문은 사용하지 않는다.
- 카드: 둥근 모서리 12–20px, 얕은 웜 브라운 그림자, 넉넉한 여백을 유지한다.
- 모션: 호버는 `translateY(-1px ~ -2px)` 또는 미세한 그림자 변화로 제한한다. 자동 재생·큰 확대·강한 반짝임은 지양한다.

## 5. 화면별 공통 적용 기준

### 축제 리스트

- 카드 이미지가 우선이며, 계절색은 이미지 위를 덮는 강한 필터가 아니라 카드 배지·하단 정보 영역·호버 상태에 제한한다.
- 혼합 목록의 페이지 배경은 기본 크림을 유지한다. 여름 카드와 겨울 카드가 나란히 있어도 화면 전체 색을 수시로 바꾸지 않는다.
- `개최중`, 날짜, 지역, 가격/무료 여부는 계절색이 아닌 읽기 쉬운 중립 텍스트와 아이콘으로 제공한다.

### 축제 달력

- 월 이동 시 해당 월의 계절색을 헤더 배경, 선택 날짜, 범례에 옅게 적용한다.
- 날짜 칸 자체는 흰색/크림 표면을 유지한다. 행사 수, 선택 상태, 오늘, 마감 임박을 색 하나로만 구분하지 않는다.
- 두 계절의 행사가 같은 날짜에 있을 때는 행사별 작은 배지에만 개별 테마를 사용한다.

### 미니게임

- 게임은 특정 축제 대표 프로그램을 미리 체험하는 장치다. 계절 장식보다 게임 규칙·점수·조작·보상 조건이 먼저 읽혀야 한다.
- 픽셀 게임에는 계절색을 지형·수집물·결과 패널의 보조색으로만 사용한다. HUD와 실패/성공 상태는 기존 픽셀 토큰과 명확한 문구를 유지한다.
- 예: 겨울 산천어 낚시는 아이스 블루를 배경·물 표현에, 가을 수확 게임은 머스터드를 수집물 강조에 사용한다.

### 사전예약·보상·커뮤니티

- 사전예약과 보상은 신뢰가 우선이므로 기본 올리브 CTA와 크림 표면을 유지한다. 계절색은 배너·보조 배지 정도로 제한한다.
- 커뮤니티의 후기·댓글은 작성 시점과 축제 태그가 먼저 보여야 한다. 계절색은 태그의 보조 정보로만 사용한다.

## 6. 계절 테마 자동 매핑

초기 구현에서는 `festivals.start_date` 또는 대표일의 **월**로 테마를 계산한다.

| 월 | 자동 테마 |
| --- | --- |
| 3월, 4월, 5월 | `spring` |
| 6월, 7월, 8월 | `summer` |
| 9월, 10월, 11월 | `autumn` |
| 12월, 1월, 2월 | `winter` |

### 기간이 계절을 걸치는 경우

1. 초기 기준: `start_date`의 월을 사용한다.
2. 날짜가 없거나 올바르지 않음: 기본값 `spring`을 사용하고, 데이터 보완 대상임을 운영 화면에서 확인할 수 있게 한다.
3. 후속 확장: 축제 기간에서 가장 많은 날짜가 포함된 계절을 계산하는 방식을 선택적으로 도입한다. 동률이면 `start_date` 기준을 유지한다.

```ts
type ThemeSeason = "spring" | "summer" | "autumn" | "winter";

// 구현 시 예시: 날짜 정보가 없으면 기본 봄 테마를 반환한다.
function getThemeSeasonByMonth(month?: number): ThemeSeason {
  if (!month) return "spring";
  if (month >= 3 && month <= 5) return "spring";
  if (month >= 6 && month <= 8) return "summer";
  if (month >= 9 && month <= 11) return "autumn";
  return "winter";
}
```

## 7. `theme_season` 확장 방향

### 사용자 화면 테마 전환

헤더의 테마 버튼은 `봄 🌸 → 여름 🌊 → 가을 🍁 → 겨울 ❄️` 순서로 화면 전체 색상을 바꾼다. 선택값은 브라우저 로컬 저장소에 유지하며, 사용자가 직접 고른 테마는 현재 월·축제 시작일·달력 표시 월의 자동 테마보다 우선한다. 이는 사용자 화면 표현 설정이며 축제 운영 데이터인 `theme_season`을 수정하지 않는다.

```text
사용자 브라우저 테마 선택 → 화면별 날짜 자동 테마 → 기본 spring
```

초기에는 날짜 기반 자동 매핑만 사용한다. 관리자가 계절을 직접 지정해야 할 실제 운영 요구가 확인된 뒤 `festivals` 테이블에 선택형 필드를 추가하는 방향을 검토한다.

```text
theme_season

spring
summer
autumn
winter
```

### 적용 우선순위

```text
관리자 수동 지정 theme_season → start_date 월 자동 매핑 → 기본 spring
```

### 관리자 기능 확장 단계

| 단계 | 범위 |
| --- | --- |
| 1단계 | 날짜 기준 자동 매핑만 사용. 관리자는 시작일·종료일의 정확성을 관리 |
| 2단계 | `theme_season`을 nullable 또는 `auto` 상태를 포함하는 선택값으로 추가. 자동 결과를 미리 보기로 표시 |
| 3단계 | 관리자 편집 화면에 `자동`, `봄`, `여름`, `가을`, `겨울` 선택과 저장 전 카드 미리 보기를 제공 |
| 운영 원칙 | 실제 축제 성격이 날짜와 다를 때만 수동 지정. 임의의 계절색으로 오래된 정보를 새 축제처럼 보이게 하지 않음 |

DB 마이그레이션, 관리자 폼, 실제 CSS 속성 적용은 이 문서 작성 범위에 포함하지 않는다. 구현 시에는 기존 마이그레이션을 수정하지 않고 새 마이그레이션과 타입 갱신으로 진행한다.

## 8. CSS 변수 구현 기준

웹 구현은 `apps/web/styles/themes.css`와 `apps/web/lib/theme-season.ts`를 기준으로 한다. 아래 핵심 토큰을 단일 원본으로 사용하고, 기존 컴포넌트 토큰은 호환 별칭으로 연결한다.

```css
:root {
  --theme-page-bg: #fff7f1;
  --theme-surface: #fffdf9;
  --theme-primary: #58734d;
  --theme-accent: #f2c2ce;
  --theme-text: #2a3626;
}

[data-season="summer"] {
  --theme-page-bg: #f0fdf9;
  --theme-surface: #ffffff;
  --theme-primary: #0077b6;
  --theme-secondary: #059669;
  --theme-text: #0f172a;
}

[data-season="autumn"] {
  --theme-page-bg: #fff5ec;
  --theme-surface: #fffdf9;
  --theme-primary: #7d5a3c;
  --theme-accent: #e9a48d;
  --theme-text: #2a1e17;
}

[data-season="winter"] {
  --theme-page-bg: #f4f9ff;
  --theme-surface: #ffffff;
  --theme-primary: #557792;
  --theme-accent: #c6e3f1;
  --theme-sub-accent: #dcd6ee;
  --theme-silver: #aeb8c2;
  --theme-text: #1e293b;
}
```

- `data-season`은 페이지 루트 또는 축제 카드 루트에 부여한다. 전역 `body`에 무조건 적용하지 않는다.
- 카드별 테마는 `data-season`과 `--theme-*` 별칭으로 국한해, 다른 카드의 색이 바뀌지 않게 한다.
- 호버·연한 배경·테두리 같은 파생색은 핵심 팔레트를 임의로 추가하는 대신 `color-mix()` 또는 검토된 별도 토큰으로 만든다.
- 여름의 에메랄드 그린은 `--theme-secondary`, 겨울의 라벤더·실버는 `--theme-sub-accent` 계열로만 사용해 주 CTA와 경쟁하지 않게 한다.
- 포커스, 오류, 성공, 비활성 상태는 계절색이 아니라 기존 의미 기반 토큰을 우선 사용한다.

## 9. 권장 문구와 피해야 할 문구

### 사용하면 좋은 표현

- `봄바람 따라 즐기는 이번 주말 축제`
- `물가에서 즐기는 여름 프로그램`
- `수확의 계절, 지역 먹거리 체험`
- `눈꽃과 함께 만나는 겨울 주말`
- `10~30초로 미리 체험해 보세요`
- `날짜와 현장 정보를 확인하고 방문을 계획하세요`

계절 단어는 실제 행사 시기·프로그램과 일치할 때만 사용한다. 문구는 분위기와 다음 행동을 함께 알려야 한다.

### 피해야 할 표현

- `무조건 인생 축제`, `지금 안 가면 손해`처럼 과도한 압박을 주는 문구
- `무조건 당첨`, `대박 보상`처럼 카지노·앱테크를 연상시키는 보상 문구
- 실제 일정·가격·프로그램을 검증하지 않은 채 계절이나 현장 경험을 단정하는 문구
- `상쾌한 블루`, `감성 코랄`처럼 색 자체만 설명하고 사용자 행동을 안내하지 않는 라벨
- 축제와 관계없는 추상 오브젝트, 과도한 꽃·눈·물결 반복 장식

## 10. 접근성과 최종 점검

- 파스텔 배경 위 본문과 버튼 텍스트의 대비를 확인한다. 흰 글자를 연한 스카이·핑크·아이스 배경 위에 직접 놓지 않는다.
- 배지 색이 달라도 텍스트로 의미가 완결되어야 한다.
- 축제 이미지가 없어도 제목, 날짜, 지역, CTA가 이해되어야 한다.
- 계절 장식은 콘텐츠·날짜·메뉴를 가리지 않으며, `prefers-reduced-motion`에서 자동 움직임을 줄인다.
- 강한 원색, 과도한 그라디언트, 복잡한 장식, 축제와 무관한 추상 이미지는 사용하지 않는다.
- 새로운 이미지 제작은 이 가이드의 범위가 아니다. 새 이미지가 필요할 경우 승인된 축제 정보와 권리 상태를 먼저 확인한다.

이 가이드는 계절마다 화면을 별개의 브랜드처럼 다시 만드는 문서가 아니다. 동일한 정보 구조·타이포그래피·여백·상호작용 위에 봄의 따뜻함, 여름의 청량함, 가을의 풍요, 겨울의 정갈함을 의미 토큰으로 적용해 축제의 시기와 현장감을 정확하게 전달하기 위한 공통 기준이다.
